# Request Identity v0 and Witness 002b

Status: pre-live-instance boundary. No ACP Job creation is authorized by this work.

## Trust claims after Witness 002

The project distinguishes these claims:

| Claim | Status |
|---|---|
| External observation obtained | PROVEN |
| Observation byte/in-pack integrity | PROVEN |
| Raw -> normalized derivation under the Observatory code | PROVEN when pack verification passes |
| Observation authenticity | NOT PROVEN |
| Request contract extraction | PROVEN |
| Local schema validation | PROVEN |
| Request byte-artifact binding | PROVEN LOCALLY |
| Deterministic PayGod decision | PROVEN |
| Decision artifacts produced | PROVEN |
| Independent verification of this live request run | NOT YET PROVEN |
| Request -> ACP instance binding | NOT YET PROVEN |
| Mandatory/non-bypassable release | NOT YET PROVEN |

A manifest proves internal consistency only. It does not authenticate ACP as the source.

## Pack verification boundary

Projection into a PayGod shadow envelope is forbidden until all available pack checks pass:

```text
raw.json
  -> byte length + SHA-256
  -> deterministic re-normalization
normalized.json
  -> existing v0 canonical SHA-256
manifest.json
  -> internal binding checks
  -> optional external manifest anchor
  -> Projection / Admission
```

The existing Observation Pack v0 is preserved so Witness 001 run `37474713196` remains replayable. Witness 002b does not rewrite that historical artifact format merely to adopt the stricter Request Identity rules below.

Important limitation:

- modifying only `normalized.json` with the old manifest must fail;
- modifying `normalized.json` and recomputing the manifest while leaving `raw.json` unchanged must fail because deterministic re-normalization differs;
- coherently replacing **raw + normalized + manifest** can pass all internal checks;
- such a coherent replacement is classified `CONSISTENT_UNANCHORED` unless a manifest/root digest is pinned outside the pack.

Therefore an external anchor is required to prevent whole-pack replacement. A matching external anchor still does not by itself prove ACP source authenticity.

## Request Identity v0

Request Identity v0 does **not** introduce another semantic JSON canonicalization protocol.

The freezer creates explicit local artifacts for:

- selected descriptor;
- observed requirements contract;
- submitted request payload.

Their identity is SHA-256 over the **exact bytes frozen for those artifacts**.

The commitment is conceptually:

```text
descriptor_artifact_bytes  -> SHA-256
requirements_artifact_bytes -> SHA-256
request_payload_bytes       -> SHA-256

request_identity =
SHA-256(exact bytes of the local request-identity commitment)
```

The repository exposes this as:

```text
workflow-observatory/request-identity/v0
byteProfile = exact-frozen-artifact-bytes/v0
```

This is intentionally conservative. Different byte representations are different request artifacts in v0 even if they parse to equivalent JSON.

### Representation rule

For v0:

```text
same bytes
-> eligible for exact identity comparison

same parsed meaning but different bytes
-> not exact
```

No semantic equivalence claim is inferred from JSON parsing.

If a later ACP instance normalizes or reorders a submitted request, that requires a separately named deterministic transform profile. It must not silently broaden `EXACT_OBSERVED`.

## request_identity, attempt_id, release_nonce

These are three distinct concepts.

### request_identity

Identifies the frozen request content, contract, and capability commitment.

Two submissions of the exact same request artifact may have the same `request_identity`.

### attempt_id

Identifies one local submission attempt.

It is generated by the Observatory/runner when the attempt is frozen and is committed together with:

- the request identity digest;
- the Observation Pack manifest digest.

The request attempt artifact uses:

```text
workflow-observatory/request-attempt/v0
```

`attempt_id` is an internal correlation key unless independently observed by the remote system. It is not proof of remote binding.

Two attempts may therefore have:

```text
same request_identity
different attempt_id
```

### release_nonce

No `release_nonce` exists in Request Identity v0 or Witness 002b.

A release nonce belongs only at the future mandatory release/enforcement boundary in Witness 005, where it can have single-use anti-replay semantics.

It must not be repurposed as request identity.

## Trust state is verifier-derived

Producer-written trust labels are not evidence.

At read/verification time, the verifier recomputes the state from the evidence it actually has.

For example:

```text
producer claims:
externalAnchorStatus = MATCHED
observationAuthenticity = PROVEN

but verifier receives no external anchor evidence

verified result:
externalAnchorStatus = UNANCHORED
observationAuthenticity = NOT_PROVEN
```

A producer claim cannot upgrade verifier-derived trust state.

## Remote binding grades for Witness 003

The following names are frozen before any `create-job` experiment:

- `EXACT_OBSERVED`: the remote instance exposes request evidence whose relevant request artifact bytes are exactly equal under the current v0 byte-exact rule, but the evidence is observed by our own acquisition path.
- `EXACT_ATTESTED`: exact byte equality plus evidence independent of the sender/observer, such as a source signature, independent reader, or independently verifiable on-chain commitment.
- `TRANSFORM_OBSERVED`: equality only after a separately named deterministic transformation profile.
- `TRANSFORM_ATTESTED`: transformed equality plus independent attestation.
- `CORRELATED_ONLY`: job/party/time/field correlation exists but exact or specified transformed equality cannot be established.
- `UNBOUND`: neither equality nor sufficient correlation is available.

Until a named transform profile exists, semantically similar but differently represented request data is conservatively `CORRELATED_ONLY`, not `EXACT_OBSERVED`.

The word **bound** must not be used without one of the exact/transform grades.

## Stable adversarial reason codes

Witness 002b requires each case to match its pre-frozen expected code.

Single-fault examples:

- `PACK_NORMALIZED_DIGEST_MISMATCH`
- `PACK_DERIVATION_MISMATCH`
- `PACK_EXTERNAL_ANCHOR_MISMATCH`
- `ADMISSION_DESCRIPTOR_NOT_FOUND`
- `ADMISSION_PAYLOAD_MISSING`
- `SCHEMA_MAXIMUM`
- `SCHEMA_TYPE_MISMATCH`
- `REQUEST_CAPABILITY_MISMATCH`
- `REQUEST_DESCRIPTOR_DIGEST_MISMATCH`
- `REQUEST_REQUIREMENTS_DIGEST_MISMATCH`
- `REQUEST_PAYLOAD_DIGEST_MISMATCH`

A negative test passes only when:

```text
actual_code == frozen_expected_code
```

Failure for a different reason is not a passing adversarial witness.

## Multi-fault precedence

The frozen rejection precedence is:

```text
PACK
-> CONTRACT / DESCRIPTOR
-> REQUEST
-> POLICY
```

Witness 002b therefore includes explicit multi-fault cases.

Examples:

```text
tampered pack + invalid request
-> PACK_* code

requirements drift + payload drift
-> REQUEST_REQUIREMENTS_DIGEST_MISMATCH

descriptor drift + payload drift
-> REQUEST_DESCRIPTOR_DIGEST_MISMATCH

payload drift + schema-invalid payload
-> REQUEST_PAYLOAD_DIGEST_MISMATCH
```

This prevents reason codes from depending accidentally on implementation branch order.

## 002b termination rule

Witness 002b is closed when:

- all frozen single-fault cases return their exact expected codes;
- coherent whole-pack replacement is classified internally consistent but externally unanchored;
- producer-written trust claims cannot upgrade verifier-derived state;
- all frozen multi-fault precedence cases return the exact higher-priority code;
- Request Identity uses exact frozen artifact bytes;
- `attempt_id` remains distinct from request identity;
- `release_nonce` remains absent;
- no ACP Agent, Signer, Job, funding, signing, invocation, or execution is introduced.

After this matrix passes against source Witness 001 run `37474713196`, stop expanding 002b.

Do not add anchoring infrastructure, a new receipt schema, or enforcement architecture to make 002b “more complete.”
